# Packet Framing Concepts

From GNU Radio

A burst transmission carries data of *yet-to-determine length*: something at
the front of each packet has to tell the receiver how much data follows and
where the payload begins. GNU Radio packets express that boundary either as **a
separate header that travels ahead of the payload** or as **a length tag that
marks the packet length inline on the stream** — two different framing
contracts, both of which end the same way: the receiver must learn the payload
length from what arrives before it.

## The length header path

The default packet header generated by `header_format_default` "consists of an
access code and the packet length. The length is encoded as a 16-bit value
repeated twice", formatted for network byte order. The formatter and parser
are two halves of one contract: the generator writes the header from a PDU,
and the header parser produces a PMT dictionary containing the fields the
payload stage needs; per the upstream docs, "All formatter blocks MUST produce
these two values in any dictionary."

Because the header and payload travel as one burst, some block has to split
them again. `digital.header_payload_demux` does exactly that: "This block is
designed to demultiplex packets from a bursty transmission. The typical
application for this block is the case when you are receiving packets with
yet-to-determine length. This block will pass the header section to other
blocks for demodulation. Using the information from the demodulated header, it
will then output the payload." The beginning of the header is identified by a
trigger signal on the block's optional second input.

Header and payload are therefore sized independently: the header's *length*
information measures what follows it, not itself. The default header
documentation makes the accounting rule explicit — "This header generator does
not calculate or append a CRC to the packet. Use the CRC32 Async block for
that before adding the header. The header's length will then measure the
payload plus the CRC length (4 bytes for a CRC32)."

## The length-tag path (no separate header block)

A tagged stream encodes the same information inline instead: "Tagged stream
blocks use tags to identify PDU boundaries: the first item of a streamed PDU
has a tag with a specific key, and that tag stores the PDU length as a PMT
integer" (see the Tagged Stream Blocks page). Regular stream blocks do not
inherently know packet boundaries, and the Stream to Tagged Stream adapter can
add length tags at regular intervals so a regular stream can be consumed by a
tagged stream block.

The Burst Tagger applies the same idea to sampled bursts: "Sets a burst on/off tag based on the value of the trigger input. This block takes two inputs, a signal stream on the input stream 0 and a trigger stream of shorts on input stream 1. If the trigger stream goes above 0, a tag with the key 'burst' will be transmitted as a pmt::PMT_T. When the trigger signal falls below 0, the 'burst' tag will be transmitted as pmt::PMT_F. The signal on stream 0 is retransmitted to output stream 0." Its GRC parameters carry the configurable key/value pairs for both events (`true_key`/`true_value` defaulting to `burst`/True, `false_key`/`false_value` to `burst`/False), turning a continuous transmission into tag-delimited bursts.

## Burst shaping and padding

`digital.burst_shaper` exists in complex (`burst_shaper_cc`) and float
(`burst_shaper_ff`) variants. Its GRC parameters are the window (float or
complex vector), pre- and post-padding item counts, a phasing flag and the
`length_tag_name`. Per the block description: "This block applies a
configurable amount of zero padding before and/or after a burst indicated by
tagged stream length tags." and "Length tags will be updated to include the
length of any added zero padding or phasing symbols and will be placed at the
beginning of the modified tagged stream." The shaper therefore operates
*within* the length-tag framing: it reads the header-side length tag, pads the
burst, and rewrites the tag so downstream blocks still see the true burst
length.

## The CRC as a frame integrity check

A frame's tail usually carries a checksum so the receiver can tell a clean
frame from a corrupted one. `digital.crc_append` receives a PDU, "calculates
the CRC of the PDU data, appends it to the PDU, and sends that as its output",
supporting any CRC size that is a multiple of 8 bits between 8 and 64; the
default parameters correspond to the CRC-32 code. The matching
`digital.crc_check` receiver "receives a PDU containing a CRC at its end, and
checks whether the CRC is correct. The PDU is sent over the ok or fail output
ports according to" the result.

In an async packet chain the order is: CRC the payload first, then add the
header (per the default header formatter's note above), so the header's length
field covers payload plus CRC — and at the receiver the frame-integrity check
runs on the assembled frame before its payload is consumed.

Which framing to use: if your packets already carry a structured fixed or
computed header, use a header formatter and the Header/Payload Demux; if the
packets are just length-delimited bursts on a tag, the tagged-stream path with
length tags needs no header block at all — only a block that is tagged-stream
compatible downstream of the tag.
