2. **D1(b) vs D1(a) are 90% the same lever.** Both are tool-keyed exemptions of `web_fetch` from tier-1 scanning; (b) additionally replaces the built-in `tool_overrides` family map (harmless for GRC — no gmail/github/ats tools) and requires manually re-declaring `enable_tier2=False` and `skip_large_arrays=False` that the capability's `__post_init__` would have set (`_capability.py:151-159`). Two knobs to keep in sync for one behavior = the duplication AGENTS.md's "simplify by removal" dislikes; (a) is the leaner of the two if the decision is "web content passes unclassified".
3. **No dead code found in the audited paths.** `shell_tools.py`'s `for_run` override, `_cwd` property, and approval re-flag are all live (AGENTS.md's "ShellToolset.for_run drops subclass customizations" verified against base `_toolset.py` returning a plain `ShellToolset`).

5. **`output_truncated` flag on every catalog return** (`src/grc_agent/adapter/rag.py:580,596` — verified) is honest, but it fires on *every* result, which trains the model to ignore it; if the fetch-limit semantics make it always true, the flag carries no information. ## 5. SMALL LOST DETAILS

1. **`enable_tier2` default trap for D1(b):** `PromptDefense.__init__` defaults `enable_tier2=True` (`prompt_defense.py:181`). The harness's own `__post_init__` deliberately passes `enable_tier2=self.semantic_detection` (False). A GRC custom defense must pass `enable_tier2=False` explicitly or it will attempt ONNX tier-2 without the ML extra. Not stated in any repo doc.
2. **`create_config` merge semantics:** `tool_overrides` is replaced wholesale, not merged (`config.py:121-124`); `field_names`/`field_patterns` keep defaults only when absent. Anyone writing D1(b) from the forensic's one-liner would silently drop the built-in SaaS-family overrides — irrelevant to GRC today, a trap if tool families are ever adopted.
3. **ConversationSearch excludes interrupted captures.** Current harness docs (`docs/conversation-search.md` via Context7): "SnapshotHistorySource recovers original messages by unioning snapshots ... while **excluding interrupted captures**." So the two lost s150 tool calls are not only absent from `sessions.messages` — they are also invisible to in-app ConversationSearch; only direct DB reads reach them.
4. **`start_command` has the same stdin shape** (`_toolset.py:422-428`) — any upstream stdin fix must cover both spawn sites (and `_BackgroundProcess` cleanup closes files, not stdin).
5. **`anyio.open_process` string commands go through `subprocess_shell`** (`anyio/_backends/_asyncio.py:2735-2740`) — so the whole command string (including `$(...)` expansions) is shell-interpreted, and `_build_cwd_capture`'s newline-wrapped form (`_toolset.py:262`) relies on that. Relevant when reasoning about any future stdin fix: `exec 0</dev/null`-style prefixes would be shell-level and command-shape-dependent — exactly the hand-picked-heuristic shape AGENTS.md forbids; the spawn-parameter fix is the uniform one.
6. **AGENTS.md's "approval mode isn't persisted anywhere" observability gap** (forensic §4.5) is still open — mode inference remains implicit in the s150 evidence.
7. **The `prompt_injection_defender` README's scope list** (installed, matches current docs): "Tool retry and failure messages raised with `ModelRetry` or `ToolFailed` are also outside its scope" — i.e., GRC's own retry/validator text is unclassified by design (matches the fs_tools malformed-`.grc` note in AGENTS.md). Worth remembering when judging D1 tradeoffs: the defender never sees our own error strings.
