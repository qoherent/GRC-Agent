# AGENTS.md

Rules for AI coding agents working on this codebase. Direct, data-driven, zero fluff.

## Architectural Vision & Core Rules

- **Simplify First**: Lean towards simplifying, not complicating. If a feature or approach is ad-hoc, hardcoded, or not essential, **remove it**.
- **No Brittle Reinventions**: Reject complex manual implementations or from-scratch logic when reliable, standard libraries can replace them. PydanticAI owns the agentic loop, tool dispatch, and message history; PyGObject's `gi.events` (or `gbulb` on older PyGObject) owns the asyncio+GTK event loop unification. Do not reimplement either.
- **No Backward Compatibility**: Delete dead code completely. Do not write shims, dual-format persistence layers, or legacy bridges. Keep changes clean and direct.
- **No Assumed Reasoning Failures**: Do not assume task failures are solely due to LLM reasoning. Audit the execution harness for context flooding, poor prompt construction, hidden ad-hoc logic, or silent error message clipping. Correctness lives at the source.
- **Maximizing Context & No String-Based Clipping**: Do not enforce arbitrary context limits beyond what the backend actually supports. Never clip inputs or outputs using raw character slicing which breaks structured context.
- **Be Bold, Objective, and Grounded**: Base every decision on grounded, verified observations, never on assumptions. Ask for clarification when requirements are ambiguous or when a major decision (e.g. library selection, backend config) needs to be made.
- **GUI-only. No CLI.** `grc-agent` is a single-entry-point native desktop app. `pyproject.toml`'s `[project.scripts]` must always point directly at `grc_agent.desktop_app:main`, launching the GUI immediately with no subcommands, no `argparse`, and no flags like `--check`/`--doctor`/`--version` beyond what GRC's own arg handling already does. If a startup-error or diagnostic need arises, solve it inside the GUI itself (e.g. a `Gtk.MessageDialog`, the sidebar's status bar) — never a command-line mode.

## Architecture at a glance

Single-process, single-thread native GTK3 desktop app. `event_loop.install()`
unifies asyncio and the GLib main loop — the agent, canvas, and all tool calls
run on one thread with zero cross-thread marshaling. GRC's own `MainWindow` is
extended in-place with a `ChatSidebar` widget (packed into the MainWindow's
existing `Gtk.HPaned` structure — no reparenting of the `DrawingArea`).

Everything lives in the installable `grc_agent` package, under `src/grc_agent/`.
It must never import from anywhere outside the package — the one accepted
exception is `ingest.py` reading the `docs/wiki_gnuradio_org/` corpus, which is
shipped package data via `pyproject.toml`'s `force-include`.

## Engineering Rules

- **No hand-picked heuristics.** No per-field allowlists, per-scenario branches, regex routing, or prompt folklore. If logic is needed, it is one uniform rule applied to every case (see `keep_param` in `adapter/graph.py`).
- **Prefer native methods.** Use GNU Radio GRC's Python API — `param.hide`, `param.category`, `Block.is_variable`, `flow_graph.is_valid()`, etc.
- **Fix at the source.** Correctness lives in the tool/handler that produces data, not in a post-processor.
- **No silent transformation.** Any truncation, filtering, or omission in model-facing output must be explicit.
- **Simplify by removal.** Prefer deleting code over adding it.
- **Evidence before assertions.** Every claim cites a verified observation, never intent. A green test is necessary, not sufficient — inspect actual data flow.
- **Prefer pydantic_ai's own sanctioned extension points** (capabilities, `ModelRetry`, `AsyncTenacityTransport`, etc.) over hand-rolled retry/loop/context logic.
- **One unified event loop, installed exactly once.** `event_loop.install()` must be called after `gi.require_version("Gtk", "3.0")` but before any asyncio/GTK usage, and `event_loop.main_event_loop()` supplies the loop `main()` runs. It picks PyGObject's in-tree `gi.events` when available (PyGObject >= 3.50; required on Python 3.14, where the unmaintained `gbulb` cannot install) and falls back to `gbulb` otherwise (Ubuntu 24.04 ships PyGObject 3.48). One capability check, not a per-distro branch — and never reimplement the unification itself. On the `gi.events` path the loop MUST come from the policy's `get_event_loop()`, which binds to GTK's default `GMainContext`; `new_event_loop()` builds a fresh `GLib.MainContext` that GTK never iterates, so GTK signals would never reach asyncio. All async work (agent streaming, runner subprocess I/O) runs on this unified loop — no `GLib.idle_add` marshaling for widget updates from async code.
- **The agent and canvas share the same `FlowGraph` object.** In the single-process app, `NativeFlowgraphProxy` forwards to `window.current_page.flow_graph`. Agent edits modify it in-place — `after_agent_edit()` refreshes the canvas (`fg.update()`, `queue_draw()`, scrolls to new blocks), re-derives the poll's sync baselines (`last_synced_export_hash`, `last_disk_hash`, the state-cache version — see the safety-net poll convention below), and pushes to GRC's native `state_cache`; no reload-from-disk is needed. Manual edits go through `sync_manual_edit()` — `fcntl.flock` on `.grc_agent/<name>.lock` (non-blocking, defer to the next poll tick on contention) around `_atomic_write_text(_serialize_flow_graph(fg), path)` + `push_undo_snapshot()` — the same lock protocol `change_graph`'s save path uses.
- **Never bump the version number without explicit user approval.** The project version in `pyproject.toml`, `CITATION.cff`, and `CHANGELOG.md` must stay in sync and must NOT be changed by an AI agent unless the user explicitly asks. A version bump is a user decision, not an agent decision — even if the agent thinks the version looks stale or inconsistent.

## Tool Surface

Six model-facing domain tools plus role-specific capability tools. The domain tools are wired in `agent.py`'s `grc_tools()`,
registered as plain `Tool(fn, name=..., description=...)` relying on
Pydantic AI's own signature/type-hint introspection. Only the planner receives
`Planning`, narrowed to atomic `write_plan` plus `read_plan`, with a durable
`SqlitePlanStore` resolved from `ctx.conversation_id == 'session-{id}'` (ungrouped
runs use `InMemoryPlanStore`). The executor receives no planning tools; a dynamic
`SystemReminders` callback renders the same store as an ephemeral, non-persisted
`<execution-plan>` handoff. `PrepareTools` removes all mutation functions from the
planner at model-request time. The other two are
provider-adaptive `WebSearch`/`WebFetch` capabilities.

| Tool | Direction | Engine |
|------|-----------|--------|
| `inspect_graph` | read | `adapter.inspect_graph()` (Stage A + B filtered) |
| `query_knowledge` | read | `adapter.query_catalog()` (catalog domain) **or** `query_docs()` (docs domain) — builds its `.db` on first use via `ingest.py` if missing. Vector search (sqlite-vec) is primary; falls back to a local SQLite FTS5/BM25 keyword search when the embed call fails or no vector index exists, tagged via `search_mode`/`message` in the tool's JSON output. Model-controlled result count via `k` (default 5, clamped 1-20). |
| `web_search` | read | pydantic-ai `WebSearch` capability — native on OpenRouter; local fallback on Ollama is upstream's `duckduckgo_search_tool` (`pydantic_ai.common_tools.duckduckgo`, backed by `ddgs`, runs off-thread via `anyio.to_thread`). Network failures raise into pydantic-ai's tool retry instead of returning a masked error string. |
| `web_fetch` | read | pydantic-ai `WebFetch` capability — native where supported, bundled markdownify fallback otherwise. |
| `generate_python` | read | `adapter.preview_flowgraph_py()` — renders the flowgraph's generated Python source via GNU Radio's own `Generator`, in-memory only (`_build_python_code_from_template()`, never `.write()`); no disk I/O. Shares the codegen validity/hier-block/C++ gate (`_check_codegen_preconditions`) and deliberately applies no `run_options` override, so it reflects the flowgraph's actual configured output. Model-controlled cap on block-source files via `k` (default 5, clamped 1-20, same convention as `query_knowledge`) — the main flowgraph script is always kept regardless of `k`; any dropped Embedded Python Block/Module files are counted in `omitted_files`, never silently. A failure (invalid graph, hierarchical block, C++ output, or an unsupported GNU Radio internal API) raises `ModelRetry`. |
| `change_graph` | write | `adapter.change_graph()` — 7-phase transactional batch mutation with rollback; a failure raises `ModelRetry` instead of returning `ok=false`. **Human-in-the-loop by default**: the tool is registered with pydantic-ai's native `requires_approval=True`, so the model's call never executes — the run ends with a `DeferredToolRequests` output, the sidebar renders an `ApprovalCard` (one-line `reason` + uniform structured summary + Approve/Deny/Always-accept), and the same turn resumes via `agent.iter(deferred_tool_results=...)` with `ToolApproved`/`ToolDenied`. The gate persists in `.env` as `GRC_AGENT_APPROVE_CHANGES` (`ask` default / `always`) and is toggled from the composer's `Mode` button (Manual = ask, Auto = apply without asking). A required `reason: str` argument (one-sentence intent) is echoed into the success payload so the persisted transcript carries the edit's intent.
| `get_run_log` | read | `exec_monitor.get_last_run_log()` via `NativeFlowgraphProxy.get_run_log()` — returns the last completed run's stdout+stderr (success or failure). Retained until the next run. When a run fails (non-zero, non-SIGTERM return code), the agent is automatically notified with the return code and prompted to call `get_run_log` for the full output — replacing the old Yes/No fix-error bubble that injected the full log as a prompt blob. |
| `save_block` | write | `adapter.block_library.save_block_to_library()` — exports an existing `epy_block` instance's source into GNU Radio's native hier-block library (`~/.grc_gnuradio`, `Config.hier_block_lib_dir`) as a new, standalone catalog block. Not an out-of-tree (OOT) module — `gr-modtool` is a separate, heavier build toolchain this app still has no access to (see `prompts.py`). Never mutates the current flowgraph's own `epy_block` instance. A failure raises `ModelRetry`, same convention as `change_graph`. |
| `read_file` · `write_file` · `edit_file` · `list_directory` · `search_files` · `find_files` · `create_directory` · `file_info` | read/write | harness `FileSystemToolset` subclassed in `fs_tools.py` (see file table) — sandboxed to the active `.grc`'s folder, dynamic per call. `.grc` reads route to the inspect engine; `.grc` writes are impossible (suffix allowlist); writes atomic; `search_files` may grep `.grc` XML (reads only). Errors surface as `ModelRetry`. |
| `read_tool_result` | read | harness `ToolOutputLimits` capability (`Spill`/`Truncate`) — any tool return over 20k chars (`Band(over=20_000)` — the library default of 10k would spill a routine ~20k `inspect_graph`) is spilled whole to `.grc_agent/tool_overflow` and replaced with a handle + bounded head/tail preview; the model reads slices back on demand (`offset`/`limit`/`from_end`/`pattern`). Lossless: `read_tool_result`'s own returns are exempt from reduction. |

## Key Conventions

- **Param filtering** (one rule, in `adapter/graph.py`'s `keep_param`): Stage A (every mode) drops `dtype == "id"`, `showports`, `bus_structure_*`, `hide == "all"`, `dtype == "gui_hint"`. Stage B (overview mode only) keeps `hide == "none"` OR `dtype == "enum"` with a non-default value or structural status OR `value != default` OR references a variable OR the param is type-controlling OR `generate_options`.
- **State values:** `enabled`, `disabled`, `bypass` (accept `bypassed` as alias). Validated against the block's own `STATE_LABELS`.
- **Block lookup:** use native `flow_graph.get_block(name)`, not a manual scan.
- **Atomic save:** temp file → fsync → `os.replace()` → directory fsync. Lock via `fcntl.flock` on `.grc_agent/<name>.lock`.
- **`change_graph` output:** returns `{"ok": true, "reason": ...}` on success; `{"ok": false, "error_type": "...", "errors": [...]}` on failure. The tool wraps this: on `ok=false` it raises `ModelRetry` with errors folded into the message. `force=True` bypasses native-validation failures only.
- **Every domain tool reports failure the same way: `raise ModelRetry`.** One uniform rule, no read/write split. `inspect_graph`, `query_knowledge` and `get_run_log` used to return the failure as a *successful* tool result (`{"ok": false, ...}`, or the string `"No execution log available — no run monitor wired."`), leaving the model to notice it on its own while `generate_python`/`change_graph`/`save_block` raised. The retry text must carry the actionable payload the caller would otherwise have to re-fetch — `inspect_graph` folds in the block-not-found list of valid block names, `query_knowledge` folds in the engine's `message`. Two deliberate carve-outs: `get_run_log`'s "no flowgraph has been run yet" stays a normal result, because an empty state is not a failure and retrying it can only waste the budget; and an unwired run monitor raises with an explicit *do not retry* instruction, because it is an environment fault the model cannot fix.
- **`_with_state_lock` is gone.** It branched on `ctx.deps.get_state_lock()`, and the only implementation (`NativeFlowgraphProxy`) returns `None` unconditionally while the scenario harness's raw flowgraph has no such attribute — so it never acquired a lock on any path and every graph tool called its callable directly anyway. Single-thread means no lock; if that ever changes, add a real one rather than reviving a no-op wrapper.
- **`change_graph` does not report `canvas_synced`.** `NativeFlowgraphProxy.notify_edit` ends in an unconditional `return {"ok": True}` and `after_agent_edit` logs GTK failures instead of signalling them, so the field could only ever be `True`. A constant success flag is worse than no flag — it reads as a checked invariant. `notify_edit` is still awaited for its side effects.
- **Graph-validity gate:** `agent.output_validator(validate_flowgraph_state)` runs on every turn's final output. If any `change_graph` tool call appears in that turn's message history, it checks the live flow graph's native `is_valid()`/`iter_error_messages()` and raises `ModelRetry` if invalid.
- **`flow_graph.validate()` must be called before trusting `is_valid()`/`iter_error_messages()`.** GNU Radio's `Element._error_messages` list is populated only by an explicit `.validate()` call and is cleared — without being refilled — by `.rewrite()`. Since every mutation path calls `rewrite()`, skipping the `validate()` call right before checking `is_valid()` makes the check vacuously pass.
- **Ports** (`inspect_graph`'s block `inputs`/`outputs`): Stage A drops hidden ports. Stage B additionally drops a port only if it is both `optional` and unconnected.
- **`type`/dtype auto-resolution:** `change_graph` accepts the literal string `"auto"` on a type-controlling param, resolved from a connected neighbor's dtype via `resolve_auto`. If a new block's type is `"auto"` but it has no already-typed neighbor to resolve from — either no connection in the batch, or only other `"auto"` blocks — the batch fails loudly with an `auto_resolve_failed` error (and rolls back) instead of silently keeping GNU Radio's own default.
- **`set_param`'s "unknown param" error lists the block's actual valid param keys** — so the model doesn't waste a `query_knowledge` round-trip guessing.
- **`resolve_auto` only ever resolves from an explicit, non-`"auto"` value** — it never guesses from an equally-unresolved neighbor, and it fails loudly instead of silently defaulting.
- **`change_graph`'s tool description is derived from its own docstring** (`docstring_format="google", require_parameter_descriptions=True`).
- **`change_graph` calls `flow_graph.rewrite()` twice** in its success path — once conditionally right after Phase 5 (`resolve_auto`), only if `add_blocks` is non-empty, since GNU Radio's `Block.rewrite()` is what populates a newly-added block's `active_sinks`/`active_sources`, which Phase 7's connection lookup (`_find_port`) needs; and once unconditionally at the end, after Phase 7 (`add_connections`), to settle all derived state before the validation gate. Both are load-bearing — the old *per-block* `rewrite()` inside the `add_blocks` loop (one call per new block) was removed and replaced by these two batch-level calls.
- **The conditional Phase-5 rewrite being gated on `add_blocks` (not on `update_params`) has a real consequence for `epy_block`/`epy_module`.** `EPyBlock.rewrite()` (GNU Radio's own code) re-parses `_source_code` and regenerates that block's ports/params only when *that block's* `rewrite()` runs — which, for a call with no `add_blocks`, only happens in the final unconditional rewrite, i.e. *after* Phase 7's `add_connections` already ran. Confirmed live: changing an existing epy_block's port count in the same call as connecting to the newly-implied port fails outright (`_find_port` can't find a port that doesn't exist yet); changing a port's *dtype* (same port key, e.g. complex→float) in the same call as connecting to it is worse — `_find_port`/`connect()` succeed against the *old* port object, then the final rewrite's `_update_ports` builds a new port object and disconnects the old one, silently dropping the connection Phase 7 just made. A dedicated post-rewrite check now catches this — and, per an adversarial-testing pass that found the first version of this check was itself incomplete on two fronts, does so correctly:
  - **Scope**: it snapshots `set(flow_graph.connections)` once, before *any* phase-3-onward mutation or rewrite (not just the connections `add_connections` itself made), and compares that snapshot against the post-final-rewrite state. An earlier version only tracked connections made in the *same call's* `add_connections`, so a call with *only* `update_params` (no `add_connections` at all) silently missed an already-existing connection dropped the same way — confirmed live, this used to return `ok: true` while a pre-existing connection vanished.
  - **Identity, not strings**: it compares actual `Connection` objects (via set membership — `Connection.__eq__`/`__hash__` are keyed on `(source_port, sink_port)`, and `Port` has no override, so this is genuinely object-identity-based), not `(block_name, port_key)` string tuples. GNU Radio can rekey a port **in place** (`Port.rewrite()` sets `self.key = self.name` on the *same* object whenever a port's dtype becomes `"message"` — e.g. a `pad_sink` reconfigured to `type='message'`), which a string-tuple comparison would misread as a dropped connection and roll back a perfectly valid batch. Comparing objects is immune to an in-place attribute mutation.
  - Rolls back the whole batch via the same unconditional `errors` list `remove_connections`/`add_blocks` failures already use — deliberately *not* just under `force`, since a connection vanishing without a word is never acceptable regardless of `force` (which only bypasses GNU Radio's own general validity opinion, not this).
  - The correct workaround, reflected in the system prompt: change an existing block's code/ports in its own `change_graph` call (no `add_blocks` in that same call), confirm the new shape via `inspect_graph`, then wire/param-set in a follow-up call — or add the block and its final code in the *same* call, since any non-empty `add_blocks` unlocks the earlier Phase-5 rewrite regardless of what's being added.
  - `change_graph_func`'s `ModelRetry` message (`agent.py`) only suggests `force=True` when `error_type == "validation_failed"` — every other failure code in the general `errors` list (including `connection_silently_dropped`) is rolled back unconditionally, so suggesting `force` there would waste one of the model's limited retries on something that can never succeed.
- **Undo/redo uses GRC's native StateCache.** Our custom disk-based undo/redo stack (`adapter/snapshots.py`) is kept for snapshot pushes during `sync_manual_edit` and `change_graph`, but the UI buttons and `NativeCanvasManager.undo()`/`redo()` methods are removed. GRC's built-in Ctrl+Z/Y works natively.
- **The whole flowgraph is relaid out from scratch by a headless, deterministic algorithm whenever a `change_graph` batch changes topology** — any of `add_blocks`/`remove_blocks`/`add_connections`/`remove_connections` non-empty, one uniform rule (the old gate, relayout only on `add_blocks`, froze wire-only follow-up calls into a stale alphabetical stack — see the add-then-wire regression test). `adapter/layout.py`'s `compute_full_layout()` classifies every block (via `classify_role`) into a header band (`variable`/`options`/`import`/`snippet` — packed left-to-right, alphabetically, options pinned first) and a flow band (everything else, positioned by `grandalf`'s Sugiyama-style rank assignment, one grid cell per block — no spiral search needed since every position is assigned together). This replaces the old "only place the new block" behavior — every existing block's coordinate is recomputed too. Runs only from `change_graph` (its only caller); manual/GUI edits (`sync_manual_edit`, the safety-net poll) never call it, so a user's own drag is never overwritten by a relayout. This must stay fully automatic since `inspect_graph` filters coordinates out of context. `_compute_ranks` is still used to feed `compute_full_layout`; the old per-new-block spiral search (`_find_block_placement`) was deleted outright once nothing but its own tests still called it.
- **The embeddings backend is chosen independently of the chat provider** (`GRC_EMBED_BACKEND`: `lexical` | `llamacpp`; default `lexical`). "lexical" uses SQLite FTS5/BM25 keyword search with zero runtime dependencies; "llamacpp" uses the local bundled llama.cpp runtime serving EmbeddingGemma-300M over a private UNIX socket with one-click GUI installation. `settings.resolve_embed_backend(cfg)` is the single source of truth; the database filename (`_lexical.db` vs `_llamacpp.db`) is keyed on the backend so switching never queries one model's index with another model's vectors.
- **The EmbeddingGemma task prefix keys on the resolved embedding *model*, not the provider** (`rag._uses_gemma_prefix`). Gemma is trained with `task: search result | query: ` / `| document: ` prefixes and is worse without them; every other model is worse *with* them. One uniform rule applied identically by `embed_query` and `embed_document`, so ingest and query can never disagree about what was indexed. (It previously keyed on `provider != "openrouter"`, which `load_settings()` can no longer return, so the Gemma prefix was being applied to every backend.)
- **`llama-server` must never be started with `--reranking`** for embeddings — it forces rank pooling and every vector comes back all zeros. EmbeddingGemma is `--pooling mean`.
- **`llama-server`'s `-b`/`-ub` must equal `-c`.** An embedding request is one sequence that has to fit in a single physical batch, and the default ubatch is 512 — so `-c 2048` alone rejects any input over 512 tokens with `input (N tokens) is too large to process`. Confirmed live: without these, the docs corpus produced a 4-row vector index.
- **The vector index is all-or-nothing** (`ingest.py`). If any embed call fails mid-build, the embeddings collected so far are discarded and the DB is built lexical-only. A *partial* `vec0` table is worse than none: queries report `search_mode: "vector"` while silently missing whatever never embedded, and no staleness check can detect it — `_db_meta` records only the model and corpus version, both of which still match. Confirmed live: 4 vector rows against 718 docs chunks ranked an AGC page top for "what is a stream tag", i.e. worse than the lexical fallback it replaced.
- **Token limits are measured, not estimated, where the backend can tell us** (`embed_runtime.fit_to_context`). `_cap_words`' 900-word cap still produced up to 2993 tokens on the shipped docs corpus, because tables/code/URLs tokenize at ~3.3 tokens per word versus prose's ~1.3. The llama.cpp path asks the server's own tokenizer instead of guessing a smaller word cap that would truncate ordinary prose to protect against the dense minority.
- **Vector DBs are built, not shipped.** `adapter._ensure_db_built` lazily calls `ingest.py` to build the catalog/docs DB on first `query_catalog`/`query_docs` call. Each backend gets its own `.db` file. `_db_meta` table stores `embedding_model` and `corpus_version`; a mismatch (or a missing lexical FTS5 index) triggers a rebuild. A per-process `_FRESHNESS_CACHE` (`rag.py`) short-circuits this metadata check entirely once a `(domain, db_path, model)` combo has been verified fresh, so it's no longer re-checked on every single query within a process's lifetime — only on the first query and after an actual rebuild. The OpenAI embed client is cached at module level for connection reuse. If every embed call fails (embedding backend unreachable), the DB is built lexical-only (FTS5, no vector index) rather than failing the whole ingest — see `query_knowledge`'s Tool Surface row.
- **The chat-sessions DB is WAL-enabled, indexed, and created directly — no schema versioning.** `db.get_connection()` issues `PRAGMA journal_mode=WAL`, which persists at the file level (the first connection flips the file to WAL; subsequent ones just read it back). It does **not** issue `PRAGMA busy_timeout`: that is per-connection, but `sqlite3.connect()`'s own `timeout=5.0` default already calls `sqlite3_busy_timeout(5000)` (verified), so an explicit PRAGMA only re-set the same value. `foreign_keys` is never set and no `ON DELETE CASCADE` is declared anywhere — every parent/child cascade is explicit SQL in `_delete_step_rows_for_conversations`/`_delete_plan_rows_for_conversations`. `init_db()` creates `sessions` plus `idx_sessions_recent(updated_at DESC, id DESC)` with plain `CREATE ... IF NOT EXISTS`; the `_meta(schema_version)` chain and its `_migrate_to_v1..v4` steps were deleted (pre-MVP, no back-compat contract). **The index is load-bearing, not cosmetic:** without it `get_recent_sessions` and `_prune_in` (which runs on every save) both plan as `SCAN sessions` + `USE TEMP B-TREE FOR ORDER BY`; its column order must keep matching the `ORDER BY`. WAL is what lets worker-thread writes overlap main-loop reads without "database is locked".
- **Message history serialization uses pydantic-ai's builtin `ModelMessagesTypeAdapter.dump_json`/`validate_json`** (`db.serialize_messages`/`deserialize_messages`). The previous `json.dumps(to_jsonable_python(...))` was a redundant double conversion (~9% larger output); the library's own one-step serializer preserves every part field — including `ThinkingPart` (reasoning), `ToolCallPart`/`ToolReturnPart`, `ModelResponse.usage` (incl. `reasoning_tokens`), and `run_id`/`conversation_id`. A malformed blob (e.g. saved by a different pydantic-ai version) logs a WARNING and returns `[]` rather than raising — surfaced in the log, not silently empty.
- **Per-turn observability and crash durability are owned by the harness `StepPersistence` capability** (wired in `agent_factory.py` on `get_step_store()`, with `agent_name="grc_executor"` or `"grc_planner"` and provider/model/base_url metadata). Every `Agent.iter()` call passes the same `conversation_id = conversation_id_for_session(session_id)` ("session-{id}") so both roles' runs/events/snapshots group under one exportable chat while remaining distinguishable by agent name. The sidebar also persists both roles' complete `ModelMessage` history, including `ThinkingPart`, in the session blob. Turns before a session row exists stay ungrouped. Full-history snapshots are unbounded (`max_snapshots_per_run=None`) so pre-compaction planner and executor traces survive for ConversationSearch and dataset collection. Deleting/clearing/pruning a session cascades all associated step and plan rows; the orphan sweep catches rows a Clear raced mid-turn.
- **Codex's `?client_version=` filters the model catalog.** It is compared against each model's `minimal_client_version`, so a pinned value silently hides newer models — 0.104.0 returned 3 and hid gpt-5.5 and the whole gpt-5.6 family. The gate describes Codex CLI features (apply-patch modes, shell types, websockets) this app does not use, since it drives the plain Responses API, so it asks for the unfiltered catalog. Keep the server's array order too: it is newest-first, while its `priority` field ranks *older* models higher.
- **Codex needs `stream: true` and an explicit reasoning summary.** Non-streaming requests are rejected outright ("Stream must be set to true"), and every model reports `default_reasoning_summary: "none"` — so without `openai_reasoning_summary` the reasoning is computed and discarded and the run's reasoning events stay empty.
- **Model ids come from the backend, not from memory** (`model_catalog.list_models`). Ollama `/api/tags`, OpenAI-shaped `/v1/models`, and ChatGPT `/codex/models?client_version=…` are all askable; the Settings dialog's model field is an editable dropdown with a Load button. Hand-picked ids are how `gpt-5.1-codex` shipped as the Codex default and was rejected with *"not supported when using Codex with a ChatGPT account"*. The HTTP path reuses `agent_factory._preflight_target` so only one place knows how to address a backend, and the response parsing lives in exactly one function: `model_catalog._list_http_models` (the Load button's parser). `agent_factory.probe_backend` is that parser plus a membership check — ONE bounded HTTP call answering "can we reach the backend" and "does it serve this model" from the same response, mapped to `(reachability_error, model_warning)`. A missing tag (e.g. `deepseek-v4-flash:0731-cloud` against a daemon serving `:cloud`) is exactly the hung-chat cause: the daemon silently pulls multi-GB while the request stays open with zero output — so Save and startup both warn in the **status bar**, never a modal popup, and never block the save.
- **`ensure_server()` is serialized by a `threading.Lock`.** Embedding fans out across `asyncio.to_thread` workers and `rag.py`'s `_BUILD_LOCKS` is per-domain, so catalog and docs cold-build concurrently. Without the lock each thread spawned its own `llama-server`: the first bound the socket and the rest died with `couldn't bind HTTP server socket`, having already overwritten `server.token` — so the survivor answered `unauthorized: Invalid API Key`. Confirmed live: three starts inside one second.
- **ChatGPT/Codex auth never touches `.env`.** OAuth access/refresh tokens live in `~/.config/grc_agent/openai-codex-auth.json`, 0600 inside a 0700 dir, written temp-then-rename. `.env` is world-readable and resolves to the *repo root* for a dev checkout — one `git add -A` from being committed. `PROVIDER_API_KEY["openai_codex"]` is `None` so the Save path writes no key line. Never log a token, an authorization code, or an Authorization header.
- **The Codex redirect URI is fixed at `http://localhost:1455/auth/callback`** — it is registered against the client id, so an ephemeral port yields a `redirect_uri` mismatch, not a working login. A pasted redirect URL or bare code is accepted as an equal-status fallback, since a remote/headless session can never receive the loopback callback.
- **Codex refresh is double-checked under an `asyncio.Lock`.** A refresh rotates the refresh token, so two concurrent refreshes invalidate each other and log the user out; several tool calls in one turn can hit an expiring token at once.
- **`openai_codex` defaults to lexical embeddings.** The Codex transport exposes no `/v1/embeddings`, so `resolve_embed_backend` cleanly uses `"lexical"` by default or `"llamacpp"` if provisioned.
- **Widgets whose visibility is provider-dependent must be synced *after* `content.show_all()`** (`ui/settings_dialog.py`). `show_all()` forces every child visible, silently undoing any `set_visible(False)` made during construction.
- **Chat model/provider is user-configurable AND live-swappable.** `agent_factory.build_interactive_agents()` reads `settings.py` and builds an executor/planner bundle over the same selected model. Twelve concrete providers remain available. Settings Save probes once, persists, calls `build_agents_from_cfg(load_settings())`, and swaps both roles through `sidebar.set_agents(...)` while preserving canonical history and the currently selected mode. The provider badge is resolved from the executor model, which is shared with the planner in v1.
- **`preview_flowgraph_py` (the `generate_python` tool) is genuinely read-only** — it calls GNU Radio's `TopBlockGenerator._build_python_code_from_template()` directly, which is pure computation with no file I/O; `write()` is the separate wrapper that actually opens/writes files, and is never called from this path (verified by direct testing: no new files appear after a preview call). It deliberately applies no `run_options` override, so it reflects the flowgraph's real configured output rather than a Run/Stop-specific one. Returns one entry per generated file — the main script plus one per Embedded Python Block/Module instance, if present, since GNU Radio's generator writes those as separate files; GNU Radio always appends the main script last, so it's kept unconditionally and only the block-source entries are capped by `k` (`omitted_files` reports the drop count). Each entry's `path` is informational only — where GRC would write it, not a real file — since at least one model has been observed formatting it as if it were a downloadable link. Hierarchical-block flowgraphs (`generate_options` starting with `hb`) are rejected outright: `HierBlockGenerator.__init__` does a real `os.mkdir()` as a side effect of construction, so there is no side-effect-free path to preview one. Reaching into `_build_python_code_from_template` (a private GNU Radio method) is a real fragility risk if a future GNU Radio version renames/removes it — an `AttributeError` there is caught and turned into a clear `ValueError` (surfaced as `ModelRetry`) rather than a confusing raw traceback.
- **GRC's Notebook/ScrolledWindow hardcodes a 600×400 minimum size** (`Notebook.py:123-124`). `NativeCanvasManager.setup_signal_handlers()` calls `set_size_request(1, 1)` on the `ScrolledWindow` to let the canvas shrink to whatever the paned divider allows.

Most ticks skip that expensive comparison entirely via a cheap gate on GRC's own `page.state_cache` version tuple (`_state_cache_version`) — the full hash only runs when that tuple has moved, or every `_POLL_FULL_CHECK_EVERY` ticks (10, ~15s) regardless, as a backstop against edit paths that don't touch `state_cache` (e.g. block-library drag-and-drop add) or the rare undo-then-different-edit tuple collision.
- **The active flowgraph is resolved dynamically** (`NativeFlowgraphProxy` in `native_canvas.py`). `drawing_area`, `path`, and `current_flow_graph` are properties that resolve from `window.current_page` on every access — tab switches are followed automatically. `get_state_lock()` returns `None` (single-thread, no races). `notify_edit()` calls `canvas_manager.after_agent_edit()` directly.
- **Compaction target is one fraction (85%) of the model's REAL context window, probed from the backend itself** (`_build_compaction_capability` in `agent_factory.py`). The window comes from `resolve_model_context_length(provider, model)` — the same probe the sidebar's context label uses: Ollama `/api/show` → `model_info.context_length` (the daemon's actual `num_ctx`, so a self-hosted server's real window is honored, not guessed), OpenRouter/OpenAI `/v1/models` → `context_length`, Codex → `context_window`. The genai-prices registry and the old 128k/32k guesses are only fallbacks when the probe cannot answer (backend down at build time, or a custom endpoint without the field) — never the primary path. `_MODEL_WINDOW_OVERRIDES` still corrects documented registry errors. `GRC_COMPACTION_TARGET_TOKENS` remains the absolute escape hatch for deployments where the fraction is wrong. **The tier knobs that matter are `keep_pairs` and `min_clear_tokens`, NOT the per-tier `max_tokens`** — `TieredCompaction` drives the tiers itself and bypasses each tier's own trigger. Verified live (session-14, 2026-08-18): with `keep_pairs=2` and no `min_clear_tokens`, a `query_knowledge` answer (~100-500 tokens) was blanked to the placeholder within one or two tool calls, so the model re-asked the same catalog question 18 times and `StopGracefully` hit the 40-request ceiling — a harness bug, not a reasoning failure. The config now keeps the last 3 pairs (harness default — the model's working room) and `min_clear_tokens=2_000`, which is a TOTAL-reclaim gate (harness semantics): when the clearable set's combined size is trivial, nothing is cleared at all — a turn of only small answers keeps them all; only when bulky `inspect_graph`/`generate_python` JSONs are present does the gate pass. Never "tune" these knobs down without re-checking that a mid-turn answer can still survive the model's next two tool calls.
- **The compaction stack ends with an LLM summary tier, not a hard window, and never destroys the training transcript.** `TranscriptPreservingTieredCompaction` wraps the production tiers (`ClampOversizedMessages` → `ClearToolResults` → `ResilientSummarizingCompaction` → `SlidingWindowCompaction`). When automatic compaction actually changes request history, it first saves the untouched `ctx.messages` — including emitted `ThinkingPart`s — as a synthetic `pre_compaction_transcript` run in the same `SqliteStepStore`; a store failure fails the turn rather than silently compacting the only copy. Manual `compact_now` likewise snapshots `_message_history` before replacing it. `ConversationSearch(SnapshotHistorySource(get_step_store()), scope="conversation")` plus `max_snapshots_per_run=None` keeps every original available in the user-exported `chat_sessions.db`. The `sessions.messages` blob remains the compacted reloadable history; snapshots are the lossless dataset/recall layer.
- **No thinking request toggle exists — by evidence, not by omission.** Verified live on Ollama (`qwen3.6`, `deepseek-v4-flash:cloud`, local + cloud): `think:true`, `think:false`, `reasoning_effort`, and no flag all behave identically via `/v1` (hybrid models think by default and the toggles are inert), and older servers only know the native-API `think` flag. The old `OLLAMA_THINKING_ENABLED` setting, Settings checkbox, and `extra_body={"think": ...}` were removed; the provider's native default stands. `ThinkingPart` display in the sidebar is unaffected.
- **The local web-search fallback is upstream pydantic-ai's `duckduckgo_search_tool`** (`WebSearch(local=duckduckgo_search_tool(max_results=5))` in `agent.py`) — the same `ddgs` engine our deleted `adapter/search.py` hand-rolled, but named `duckduckgo_search` (the old bare-callable wrapper surfaced under the wrapped function's name instead). **The system prompt deliberately does not name it, or any tool.** The name is provider-dependent by construction: `OllamaModel.profile['supported_native_tools']` is empty, so `_resolve_request_tools` keeps this local fallback, while a provider with native support gets `web_search` and this one is dropped — so no static list in the prompt can be correct on every backend. A prompt that claimed `web_search` shipped, and the guard test written to prevent exactly that drift hardcoded the same wrong name and off-thread via `anyio.to_thread`, so it never blocks the unified event loop.
- **Filesystem tools are sandboxed to the configured project directory, one uniform rule per concern** (`fs_tools.py`). Root: the explicit project directory selected in the sidebar (persisted in `GRC_PROJECT_DIR`), re-resolved per tool call from `desktop_app`-installed providers (`set_active_graph_providers`) with fallback to the active `.grc` file's folder. An unset root gates every tool with a clear ModelRetry. `.grc` reads route through the `inspect_graph` engine (active file → live `FlowGraph` object; other `.grc` in the folder → headless `load_flow_graph` on the cached `get_platform()` singleton) — raw XML never reaches the model; `.grc` writes are structurally impossible (the write rule is a suffix allowlist: `.py .cmake .txt .md .m .json .yml/.yaml C/C++ .xml .conf .rst .i` — OOT-module-ready, deliberately excluding `.grc`). Writes go through `adapter._atomic_write_text` (temp → fsync → `os.replace`), preserving the harness's parent-must-exist/`expected_hash` contracts. Denied outright: `.env`, `.env.*`, `.grc_agent/*`, `.git/*` — each also in a `**/` form so NESTED files (`pkg/.env`, `.venv/.env`, `sub/.git/config`) are covered too (fnmatch `*` spans `/`; the harness `_matches` strips a leading `**/` for the root case) — on top of the harness-protected defaults. The flowgraph-name rule is one uniform test, not a per-form list: any path whose name contains `.grc` (case-insensitive) is routed to the inspect engine on read (`_is_grc_name` — covers `.grc`, `.grc~`, `.GRC`), and the write gate applies the same test to BOTH the requested name and the symlink-resolved target (an in-root `alias.py` → `real.grc` can't smuggly a flowgraph write). Caps: `max_read_lines=1000`, `max_list_results=200` (0.22+ semantics: explicit truncation marker only when an entry was actually dropped). `search_files` may grep `.grc` XML — reads are the harmless direction. The `_root`/`_real_root` properties swallow the parent `__init__`'s static assignments so the dynamic value is authoritative; `_safe_resolve` is the single gating chokepoint every tool funnels through. A malformed `.grc` raises a FIXED-text `ModelRetry` (parse exceptions interpolate file content, and retry text is not classified by the injection defender) — details go to the log.
- **Every client-executed tool result is classified for indirect prompt injection** (`prompt_injection_cap` in `agent.py`, wired in `agent_factory.py`). The agent ingests untrusted text (user project files via the fs tools, web content via the `web_fetch` local fallback) and can write files, so tier-1 pattern detection (stackone-defender, no ML extra, no network) runs over every tool result and a high/critical-risk result is withheld and replaced with a short notice; flags are logged via `_log_injection_detection`. Measured cost on the unified loop: ~0.5ms/KB (6ms for a 40KB `inspect_graph`, 48ms for a 100KB `read_file`) — same class as the app's existing sync file I/O there, accepted out-of-box rather than wrapping the defense in a thread. Known scope limits: provider-native web tools run server-side (never classified), `ModelRetry` failure text is our own strings, non-text media is not decoded, and tier-1 pattern detection only inspects recognized text fields + bare string results — strings nested under OTHER keys (e.g. inside `inspect_graph`'s JSON `params.value`) are not classified without the ML extra (verified live on stackone-defender 0.7.4). `FallbackCompaction` (0.23) was evaluated as a replacement for `ResilientSummarizingCompaction` and NOT adopted: `TieredCompaction._escalate` re-measures after each tier and continues past a tier that returned history unchanged (verified in source), so the wrapper's return-unchanged failure path already escalates to the SlidingWindow tier — FallbackCompaction would add nesting with no semantic gain, and its narrow default `fallback_on=(ModelAPIError,)` would need live Codex re-verification before narrowing our catch.

- **`_sha256_file` uses `hashlib.file_digest`** — streams the file instead of loading it entirely into memory.
- **`_scroll_to_relaid_out_graph` multiplies coordinates by `zoom_factor`** — scroll targets are in zoomed space. Targets the new blocks' POST-relayout coordinates (the actual "what changed" location — the relayout runs inside `change_graph` before this is called), falling back to the whole graph's `get_extents()` bounding box only if the new blocks carry no coordinates.
- **`get_run_log` reads the last run's output from `exec_monitor`.** The monitor retains `_last_run_log`/`_last_run_code` (success or failure) until the next run starts. The 512 KB `deque` cap drops the log's **oldest** chunks, so the payload sets `log_truncated`/`truncation_note` when that happened — the reduction has to be visible or the model reads a partial diagnostic as a complete one (`_last_run_evicted` is frozen at Done time for the same reason `_last_run_had_runtime_error` is: `_reset()` clears the live flag). When a run fails (non-zero, non-SIGTERM return code), `ChatSidebar.notify_run_failure` sends a short agent notification with the return code — the full log is NOT injected as a prompt; the agent calls `get_run_log` as a structured tool result. The tool is wired through `NativeFlowgraphProxy.get_run_log()` (which bypasses `__getattr__` forwarding via `object.__getattribute__`) — no module-level singleton.
- **Incremental `force=True` editing is a taught strategy.** The system prompt explicitly tells the agent it may split a large edit across multiple `change_graph` calls in one turn, using `force=True` on intermediate calls that leave a required port temporarily unconnected — the environment re-validates only the final state at turn end (`validate_flowgraph_state` in `agent.py`). Structural error messages (`add_connection_failed`, `auto_resolve_failed`) include port dtype details so the model can diagnose mismatches and decide whether to split, insert a converter, or change a type. Each call still pauses for approval (unless the gate is `always`) — the denial feedback (`ToolDenied`) goes back to the model natively, and the prompt forbids re-submitting a denied edit.
- **The approval pause is a mid-turn resume, not a second turn.** `_run_agent_turn` loops `agent.iter()` segments: when a run ends with `DeferredToolRequests`, its messages are persisted to canonical history immediately, the approval cards render into the streaming row, and the same turn resumes with `deferred_tool_results=` (no new user prompt). The final transcript is rebuilt from canonical history (`_render_history`) so both the pre-approval tool call and the resumed answer render. The tool never executes before approval — so the 1.5s safety-net poll has no unapproved in-memory mutation to auto-write, by construction.
- **Verifying "did it actually work" (not just "did it run") is a taught strategy, not harness code.** `get_run_log` already returns the full unfiltered stdout/stderr, including GNU Radio/UHD's single-character streaming diagnostics (`aU`/`uO`/etc.) — nothing is hidden from the model. Hardcoding an interpretation table for those codes, or hardcoding "missing throttle"/"Nyquist violation" preflight checks into `inspect_graph`, would both require interlocking per-block-type allowlists — exactly the heuristic pattern the no-hand-picked-heuristics rule forbids. Instead the system prompt teaches one uniform rule: wire a native diagnostic block (`blocks_probe_rate` → `blocks_message_debug`, or a signal-magnitude probe) into the flowgraph before asking the user to run it, then read `get_run_log`. Verified live: `blocks_probe_rate`→`blocks_message_debug` prints structured values to stdout with zero custom code, and GRC's generated SIGTERM handler (`tb.stop(); tb.wait()`) means a user-initiated Stop still flushes and captures any buffered probe output. ControlPort (Thrift RPC) is real and compiled into GNU Radio but would need new harness code (endpoint discovery, a Thrift client) for a capability — live mid-run polling without stopping — not required here; shelved.
- **`save_block` (`adapter/block_library.py`) exports an `epy_block` instance into `~/.grc_gnuradio` (`Config.hier_block_lib_dir`) as a standalone catalog block** — GNU Radio's native, lighter "hier-block library" mechanism, distinct from an out-of-tree (OOT) module (`gr-modtool`), which this app still has no access to. Derives the `.block.yml`'s params/ports from `gnuradio.grc.core.utils.epy_block_io.extract()` — the same introspection `EPyBlock.rewrite()` already uses. Every param gets `dtype: raw` uniformly (matches `EPyBlock._update_params()`'s own convention, not a guessed per-param dtype). The `.py` source is copied byte-for-byte; only the filename changes (the live instance's module name is flowgraph-and-instance-scoped, `<flowgraph_id>_<instance_name>`, unsuitable for a standalone reusable file). The exported block's `templates.imports` line is `import {block_id} as {block_id}  # grc-generated hier_block` — the trailing comment is load-bearing, not decorative: `TopBlockGenerator._imports()` greps every block's imports line for that exact suffix to decide whether to inject the `sys.path.append(...~/.grc_gnuradio...)` hack into a generated flowgraph script; omitting it makes the block silently unimportable from any flowgraph that isn't itself a hier block. Never mutates the current flowgraph's own `epy_block` instance — the saved block is a separately-`block_id`-named catalog entry for *future* use only.
  - **`gnuradio.grc.core.platform.Platform.block_classes` is a single `ChainMap` defined as a Platform CLASS attribute** (`block_classes = ChainMap({}, block_classes_build_in)`), and `Platform.__init__` does `self.blocks = self.block_classes` — a reference, not a copy. Every instance of THAT class (the headless `Platform` `get_platform()` builds — including a freshly-constructed "throwaway" one) therefore shares the exact same underlying dict; there is no way to get an isolated headless block registry by constructing a new headless `Platform`. (`gnuradio.grc.gui.Platform.Platform`, the class `get_gui_platform()` builds, is a separate subclass that overrides `block_classes` with its own independent `ChainMap` — confirmed live — so the GUI registry and the headless registry are genuinely two different dicts; this feature only ever constructs headless instances for validation, so the shared-dict risk below is specifically a headless-`Platform`-vs-headless-`Platform` hazard, not a headless-vs-GUI one.) Confirmed live: calling `build_library()` on any headless instance — including a brand-new, never-cached `Platform()` — clears and rebuilds that ONE shared headless registry for the WHOLE PROCESS, silently wiping the real `get_platform()` singleton's `'options'` block process-wide. `save_block`'s validation step (`_validate_block_definition`) therefore never calls `build_library()` at all — it validates via `Platform.new_block_class()` (== `blocks.build()`), confirmed live to be a pure function with no such side effect, instantiating the resulting class directly against a throwaway `FlowGraph` from the real `get_platform()` singleton. It deliberately does **not** call `block.validate()`/`is_valid()`: a freshly-instantiated, unwired, un-id'd block always reports "Port is not connected" and "ID must begin with a letter" — both artifacts of validating a standalone instance outside a real flowgraph, not defects in the exported definition — matching this module's own `_throwaway_block()` precedent (`graph.py`), which never calls `validate()` for the same reason.
  - **Block-id collisions are gated by one uniform rule, not a hardcoded blacklist.** GNU Radio's own loader does not raise on a duplicate id — it silently overwrites unless the id belongs to a genuine built-in. `_check_block_id_available` looks up the existing block's `loaded_from` path and checks whether its parent directory is `hier_block_lib_dir()` — i.e., whether it's a block this tool itself saved previously, not a stock or foreign one. Only an id that's ours can ever be overwritten (and only with `overwrite=True`); a stock/foreign id is always rejected regardless of `overwrite`.
  - **Refreshing the catalog after a save has two independent layers, both required.** `get_platform().build_library()` alone is not enough — `rag.py`'s `_CORPUS_VERSION_CACHE`/`_FRESHNESS_CACHE` (per-process, keyed by domain) short-circuit the staleness check once verified fresh, so without popping `"catalog"` from both, `query_knowledge` would keep silently returning stale results (missing the new block) for the rest of the process's life. The live GUI block-tree panel is refreshed separately via `NativeCanvasManager.reload_block_library()`, mirroring GRC's own native `RELOAD_BLOCKS` action (`self.platform.build_library(); main.btwin.repopulate(); main.update_pages()`) — using `self.platform` (the GUI `Platform` backing the live `MainWindow`), never the headless `get_platform()` singleton, since they are separate instances and only rebuilding the right one updates the visible panel.

The clustered unit files share fixtures/helpers via `tests/conftest.py`
(flowgraph fixtures, epy sources, probe `_FakeResponse`, session seeders) —
do not re-split them per test. The sidebar/dialog/canvas tests build real GTK
widget trees and need a display (`xvfb-run`); the graph/layout/db/exec tests do not.

`test_isolation.py` and the live-network tests (lite.duckduckgo.com search,
Ollama embeddings/chat for RAG) are not fully hermetic. `test_isolation.py`
needs no GUI/display server; the sidebar/dialog/canvas clusters (test_chat_sidebar,
test_native_canvas, test_desktop_app) build real GTK widget trees and need
one (`xvfb-run`). `test_session_persistence.py` is fully hermetic (each test redirects
`GRC_AGENT_ENV` to a fresh tmp path). `test_session_persistence_advanced.py` uses
pydantic-ai's `TestModel` for real-agent-integration tests (no LLM, deterministic),
plus concurrency stress tests (multi-thread writes, WAL validation), data-integrity
edge cases (Unicode/emojis/large blobs), schema migration coverage (v1/v2/v3 → v4),
and end-to-end ChatSidebar tests (real widget tree under xvfb + real agent.iter() loop
→ StepPersistence runs/events/snapshot rows in the DB). `test_integration.py` defaults to Ollama Cloud (the project's
standard real-LLM test backend) when `OLLAMA_CLOUD_API_KEY` is configured — it
does not also run against local Ollama/OpenRouter just because they happen to be
available too. Force a specific backend with `GRC_TEST_BACKEND=ollama|ollama_cloud|openrouter`.

Tests that need a real GTK widget tree require `xvfb-run` (e.g. `xvfb-run -a uv run pytest`).
